# 《一票入场》前端 V0.1 开发规格

## 1. 目标

以“领取一张戏票，进入一场真实的上海演出”为主线，先完成可演示、可扩展、便于后续接入后端 API 的前端原型。

V0.1 同时服务两类用户：

- 舞台漫游用户：通过选形象、领戏票、看演出、认识人物、走进场馆、收集印章完成体验闭环。
- 全量检索用户：浏览全部 834 张戏单，并按关键词、年代、剧种、场馆和关联状态筛选。

## 2. 本次实现范围

- P01 首页
- P02 形象选择
- P03 虚拟戏票大厅
- P04 戏单列表 / 搜索筛选
- P05 戏单详情（有确认关联、暂无确认关联两种状态）
- P06 人物后台
- P07 人物详情模板
- P08 虚拟上海试点页
- P10 我的舞台护照基础版
- P12 项目说明页

场馆全量详情、AI 漫游纪念册、完整 3D 场景和登录系统不属于本次实现范围。

## 3. 路由

| 路由 | 页面 |
|---|---|
| `/` | 首页 |
| `/persona` | 形象选择 |
| `/lobby` | 虚拟戏票大厅 |
| `/tickets` | 戏单长廊 |
| `/tickets/:nid` | 戏单详情 |
| `/people` | 人物后台 |
| `/people/:id` | 人物详情 |
| `/shanghai` | 虚拟上海 |
| `/passport` | 我的舞台护照 |
| `/about` | 项目说明 |

## 4. 数据访问边界

页面组件不得直接读取大型 JSON，也不得在组件中硬编码后端 URL。统一通过 `src/data/repository.ts` 暴露的数据仓储接口读取数据。

开发阶段使用 `MockRepository`；后端完成后增加 `ApiRepository`，页面和组件不需要改写。

核心数据类型：

- `TicketSummary`：戏单卡片、搜索和筛选所需字段。
- `TicketDetail`：戏单详情、剧目、演员、机构、关联和证据。
- `PersonSummary` / `PersonDetail`：人物后台和人物详情。
- `VenueSummary`：虚拟上海和场馆入口。
- `PassportState`：用户形象、收藏、浏览记录和印章。

## 5. 数据与史实边界

- 只有经过人工审核的关系才能显示为文化关联。
- A 级表示直接 URI 关联；B 级表示经人工审核的推断关联。
- 暂无确认关联的戏单仍完整展示基础信息，不显示空关系图。
- 字段推荐必须标明“基于戏单字段推荐”，不得伪装成审核关系。
- 无戏单原图时显示“数字戏票”，并注明依据上海图书馆开放数据生成。
- 无开放人物照片时使用统一剪影，不生成虚假真人头像。
- 场馆没有可靠历史资料时仅显示地点线索，不补写建筑史。

## 6. 本地状态

V0.1 不要求登录。以下状态保存到浏览器 `localStorage`：

- 已选择形象
- 收藏的戏单 nid
- 已浏览戏单 nid
- 已认识人物 id
- 已到访场馆 id
- 已获得印章

## 7. 页面状态

核心页面必须具备：正常、加载、空结果、部分字段缺失、无图片五种表现。API 暂时失败时应保留已加载内容并给出提示。

## 8. 验收标准

- 导航和所有上述路由可访问。
- 首页能清晰区分“开始舞台漫游”和“浏览全部戏单”。
- 可选择形象并在刷新后保留。
- 戏票大厅支持随机、按年代、按剧种领票。
- 戏单列表支持关键词、年代、剧种、场馆和关联状态筛选。
- 两种戏单详情状态表达清楚，暂无关联不被弱化成无效数据。
- A/B 证据可见并能查看来源和 URI。
- 人物无照片时显示统一剪影。
- 收藏、浏览记录和印章可在护照页查看。
- 桌面端和移动端主要页面均可正常使用。
- `npm run build` 和前端自动化冒烟测试通过。
